## 二、Ex18：把“比较规则”和“排序算法”作为参数

今天从 `typedef` 和排序主程序继续，把函数指针用到了完整程序中：

~~~c
typedef int (*compare_cb)(int a, int b);
~~~

`compare_cb` 是函数指针类型；`cmp` 指向具体比较函数。调用链为：

~~~text
main
  → test_sorting(numbers, count, sorted_order)
  → bubble_sort(numbers, count, cmp)
  → cmp(a, b)
  → sorted_order(a, b)
~~~

使用输入 `4 1 7 3 2 0 8` 时，对话中确认的三组输出为：

~~~text
0 1 2 3 4 7 8
8 7 4 3 2 1 0
3 4 2 7 1 0 8
~~~

第三行是 `strange_order` 在本次输入和冒泡实现下的结果；它不代表常规升序或降序，也不能要求不同算法给出相同的“奇怪顺序”。

同时复习了 `argc/argv`、`argv + 1`、`atoi`、`malloc`、`memcpy` 和 `free`。原数组由 `main` 申请和释放；排序函数申请副本并返回，`test_sorting` 负责释放返回的数组。

最后增加选择排序，将算法也作为参数：

~~~c
typedef int *(*sort_cb)(int *numbers, int count, compare_cb cmp);
~~~

现在 `sorter` 决定使用冒泡还是选择排序，`cmp` 决定升序还是降序。`ex18_extra` 截图确认：

~~~text
Bubble sort:
0 1 2 3 4 7 8
8 7 4 3 2 1 0

Selection sort:
0 1 2 3 4 7 8
8 7 4 3 2 1 0
~~~

## 四、Valgrind：两次报告需要分别理解

### 1. Ex18 NULL 回调：非法跳转导致异常终止

用户贴出的报告包含：

~~~text
Jump to the invalid address stated on the next line
at 0x0: ???
Process terminating with default action of signal 11 (SIGSEGV)

in use at exit: 1,080 bytes in 3 blocks
definitely lost: 0 bytes in 0 blocks
indirectly lost: 0 bytes in 0 blocks
still reachable: 1,080 bytes in 3 blocks
ERROR SUMMARY: 1 errors from 1 contexts
~~~

这是故意传入 NULL 的实验结果。虽然 `definitely lost` 为 0，程序仍然发生了非法调用，不能写成“Valgrind 通过”或“所有内存均已释放”。

### 2. Ex19：退出时存在未清理的对象

在新增 Cellar 之前，用户贴出的报告是：

~~~text
in use at exit: 608 bytes in 12 blocks
total heap usage: 14 allocs, 2 frees, 2,656 bytes allocated

definitely lost: 64 bytes in 1 blocks
indirectly lost: 544 bytes in 11 blocks
still reachable: 0 bytes in 0 blocks
ERROR SUMMARY: 1 errors from 1 contexts
~~~

本次对象布局与原地图对应：Map 本体 64 字节，另外连接着房间、怪物和描述字符串。程序退出时没有销毁整张地图，因此产生直接和间接泄漏。

今天完成的是**发现、解释泄漏**。没有完成 `Map_destroy()` 和完整资源释放，也没有最终版本“零泄漏”的新报告。**608 字节只对应当时四个房间、一个怪物的版本**，不能直接套用到扩展地图或森林游戏。

## 五、Ex19：从对象行为到多文件工程

本章通过结构体保存数据和函数指针：

~~~text
Object：描述与默认行为
Monster：血量、攻击和初始化
Room：怪物、四个方向的房间指针
Map：起点、当前位置及操作转发
~~~

移动与攻击的主要调用链为：

~~~text
n/s/e/w → process_input → Map_move → Room_move → 更新 location
a       → process_input → Map_attack → Room_attack → Monster_attack
~~~

怪物初始血量为 10，每次 `rand() % 4` 产生 0～3 点伤害，所以攻击几次后仍存活是正常现象。今天实际观察到了怪物死亡，但当前实现仍保留死亡怪物，尚未加入销毁并清空 `bad_guy` 的逻辑。

审计时检查了对象及函数指针是否有效、`NEW()` 与分配结果、方向和伤害参数、分支及返回值，并将输入处理改为：

~~~c
int ch = getchar();

if (ch == EOF) {
    return 0;
}
~~~

`assert` 有助于暴露错误状态，但不会自动清理资源，也不等于完整错误恢复。
